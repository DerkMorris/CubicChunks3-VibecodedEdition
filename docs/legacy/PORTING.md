# Fabric 26.3 port status

This is an experimental source port of the unfinished CubicChunks3 rewrite. **Cubic world creation, client entry, save/reopen, and automatic sky/block lighting now work with the current hills generator.** This is not a finished survival release: extreme-height rendering, fluid/block ticks, caves, ores, vegetation, structures, complete village gameplay and further lighting performance work remain unfinished. Earlier mob, POI, editing, and persistence components retain their regression tests.

Upstream base: `OpenCubicChunks/CubicChunks3` at `e23e0e42`; branch: `port/fabric-26.3`.

## Initial cubic world generation and entry

The reported 2026-10-28 crash was the deliberate `requirePlayableCubicWorld` restriction in the Level constructor. That restriction and the temporary client refusal screens have now been removed after implementing and exercising the entry path. Enable Cubic Chunks for a **new test world**, either in the creation screen or with `general.generateNewWorldsAsCC=true`. Creative/Peaceful is the tested configuration. The tooltip describes the unfinished generation and lighting. Other terrain presets currently use the same cubic hills.

`level.dat` stores `cubicchunks:world_format=1`. A missing marker means an ordinary existing world, regardless of the new-world preference; unknown versions fail loading. Only the Overworld becomes cubic. Nether, End, and custom dimensions retain the ordinary path. A configuration-phase Fabric payload sends the saved mode before the client level is constructed; a client without that payload cannot join a cubic server.

`CubeTerrainGenerator` evaluates smooth seeded hills using absolute X/Z, with grass, three dirt layers, stone beneath, and air above. It does not repeat a floor at each cube boundary. Biomes use the configured native biome source and absolute quart coordinates in all eight sections. Structure, feature, generation-spawn and light stages remain placeholders. The independent-terrain status pyramid only requires an EMPTY neighbor ring for FULL promotion; ordinary metadata columns retain their native dependencies.

The real 26.3 entry path required full-coordinate initial load counts, cube-aware latest status, completed FULL-promotion confirmation, three-dimensional spawn tickets and entity waits, and corrected object/key sorting in both player-send branches. Native column lifecycle callbacks no longer cast a cube to a LevelChunk. Render-graph readiness now follows loaded block cubes, allowing the level loading screen to finish while unknown light remains zero/unready. Exact light arrivals still rebuild sections; no maximum-light substitute or false `isLightCorrect` flag was introduced.

The mixed 2D/3D loading graph retains intermediate cube distances after its smaller generation radius releases a holder. This lets ticket removal propagate through the remaining metadata columns, fixing shutdown with an empty ticket set but thousands of stranded columns. Empty entity stores no longer rewrite an empty file for every loaded cube on each unload. That initial persistence milestone acknowledged disk work synchronously; its tested save took roughly 25 seconds; the storage optimization below reduced a later fresh-world measurement to roughly 12 seconds.

The optional development mod in `port-tools/world-smoke` drives the **real client and integrated server**, production storage, mode negotiation and renderer. It is excluded from the release JAR. With `IS_IN_TEST=false`, it created `entry-final`, observed grass under the player, a closed loading screen and visible sections, received a gold-block update, then stopped cleanly. A fresh process reopened the same world with the new-world preference disabled and observed that gold block in a cubic client level, then stopped cleanly. Logs: `build/world-entry-final-create.log` and `build/world-entry-final-reopen.log`. This establishes the initial entry/save/reopen path, not multiplayer, traversal at extreme heights, complete simulation, or visual lighting correctness.

## Save performance follow-up

A Java Flight Recorder profile of a real new-world save showed the I/O workers spending most sampled time opening files, writing them and forcing them. The old path created a temporary file, reopened it for compressed NBT output, reopened and decompressed it for validation, then reopened it again for forcing. `CubeStorage` now compresses and validates the same bytes in memory before writing them through one FileChannel (handling partial writes), forcing, closing and atomically replacing the destination. This avoids the extra NBT output/readback file opens and the truncation path. Terrain, entities and POI all use this backend.

The 64 MiB decoded-NBT accounting limit, depth validation, detached snapshots, FIFO read/write/delete order, flush/close failure reporting, exclusive writer lock, per-file force and atomic replacement remain in place. No storage schema or migration changed. Validation still rejects unreadable replacements before replacing committed data. Compression adds a temporary byte buffer per active I/O worker; large individual tags can therefore increase transient memory use. At that milestone callers still waited synchronously for acknowledgement; the asynchronous follow-up below replaces those waits during autosave and normal unload. The backend still saves one compressed file per cube.

The real-client runs used the same seed, Creative/Peaceful mode and view-distance settings. Times below are the approximate interval from `Saving worlds` to the final `Saving chunks` messages, not application startup time. Live generation produced different file counts; this is a local measurement, not a controlled throughput guarantee for every world or disk.

## Asynchronous autosave

Terrain, entity and POI snapshots now go through owner-thread acknowledgement queues. Each queue admits at most 32 pending writes and 64 MiB of NBT accounting size; the same cube cannot have two writes pending. Normal terrain autosave/unload passes prepare at most four cubes, and POI/entity ticks submit at most four writes. Backpressure retains dirty cubes and schedules retries instead of blocking the server. Native ordinary-dimension persistence is unchanged.

Snapshots are detached on the owner thread. Successful acknowledgement does not clear edits made after capture. Failures restore terrain/POI dirty state, retain pending unload holders and entities, and remain visible to flush/close; cleanup releases storage locks even after failure. The existing compressed-NBT format, strict validation, per-file force and atomic replacement are unchanged. Proto/FULL overwrite checks now execute in the same FIFO operation as their write. Entity autosave loads missing destinations asynchronously before validating the moving-entity batch, and unload compares current entity state with acknowledged snapshots before releasing UUIDs.

These are queue accounting limits, not a total JVM-memory ceiling: backend copies, compression buffers, the latest acknowledged entity batch and the active entity batch can coexist. Entity batches are separately limited to 64 MiB of NBT accounting size and fail explicitly if exceeded. Snapshot serialization still runs on the server thread, and entity batch capture still scans resident entities. Initial loading/generation, synchronous reads for explicit cube/POI loads, native player/level metadata saves and explicit flush/exit can still pause. Multi-file batches remain non-transactional after crashes.

Real-client validation (`async-save-02`, Creative/Peaceful, render distance 2) held the terrain worker behind a latch, captured a diamond block, ran normal non-flushing autosave, and changed the block to emerald before releasing disk writes. Autosave plus both block updates returned in **21 ms**, and the server advanced **30 ticks in 1.5 seconds while disk writes remained blocked**. The client exited normally, and a fresh process reopened both the gold marker and the newer emerald block with the new-world cubic preference disabled. No test-mode storage or `IS_IN_TEST` bypass was used. Logs: `build/async-save-world-02.log`, `build/async-save-reopen.log`.

An earlier probe during initial loading returned from autosave in 16 ms but advanced only four ticks and failed its tick-rate assertion. Probe code stays outside the distributed mod.

## Automatic cubic world lighting

`CubeWorldLightManager` starts on normal cubic server ticks and prioritizes FULL cubes in players' tracking views, including cubes pending their first send. The scheduling optimization below admits up to eight background calculations, prepares up to 32 captures with a 4 ms soft owner-thread budget, and delivers at most 16 publication notifications per tick. The calculation retains no mutable world or holder references. Column revisions, cube identity and block revisions reject stale completions. Edits revoke affected and adjacent X/Z columns at every loaded Y, so changing a roof also invalidates light far below it. An unchanged captured source can retire into the saved foundation after unload acknowledgement; missing or revision-mismatched captures discard that foundation and force a fresh read.

`CubeWorldLightSolver` solves a 32-cubed target with a 15-block halo (62-cubed working volume). Every non-direct transfer loses at least one level, so attenuated light outside the halo cannot reach the target. Direct level-15 sky sources come from `CubeWorldSkyColumn`, which checks native directed occlusion edges throughout saved/live vertical coverage, including cross-cube boundary faces. It overlays live generated cubes on saved section data and uses the exact seeded hills generator for genuinely absent or pre-terrain data. Unknown or corrupt files fail the calculation instead of becoming air. The existing bounded obstacle/surface query APIs keep their separate unknown-coverage semantics.

That generator fallback is specific to the port's current grass/dirt/stone hills. Adding caves, ores, structures, feature placement or another generator requires updating it or replacing it with authoritative generated observations. It is not a general solution for arbitrary modded generators. Saved column scans retain their existing 16,384-file / 128 MiB aggregate-NBT / one-million-entry limits. The live snapshot cache is capped at 4,096 cubes; reaching that cap within a required column neighborhood reports a failed calculation and retries. Disk block/column caches each retain at most 128 futures; decoded column maps and active work have additional memory costs. Full column rebuilding and conservative invalidation still need performance work for large worlds and large view distances.

Full-cube outer wire format **4** adds a validated per-cube publication flag. Scoped revocations remove only the specified cube; unrelated ready views survive newer epochs. Complete block and light snapshots remain bound together. Client predictions revoke dependent columns and also reject old callbacks queued before their first light entry was installed. Recovery republishes ready views in the affected column neighborhood with fresh epochs, using the existing tracking checks/rate limit. Disk format 2 stays unchanged: light is recomputed on load, and `isLightCorrect` remains false. The old bounded API is retained for explicit diagnostic/test use before automatic lighting starts; an explicit bounded rebuild cannot replace an already active automatic manager.

The detached automatic solver is compared cell-for-cell against the actual 26.3 light engine in scenes containing water, leaves, slabs, stairs, roof openings and cube-boundary sources. Tests also cover both signs of 32 million Y, source/roof removal, stale work, independent client epochs, queued callbacks, malformed packets, and an unloaded saved roof 100 cubes above the target after reopening storage.

Real client/integrated-server run `world-light-02` passed surface sky, source placement, solid roof, source removal, roof removal, and underground source/removal at Y near +32,000,000 and -32,000,000. ## Lighting scheduling and initial publication (2026-10-29)

The previous queue completed at most one cube per server tick even when workers had capacity. The manager now admits up to eight jobs and publishes all completed current results in one tick. Cubes within one cube of an edit take priority over the remaining vertical-column backlog. Capture prepares up to 32 snapshots per tick and stops after a soft 4 ms budget (a single capture can exceed it). Full block arrays are copied only for the 3x3x3 propagation halo; other heights contribute sky summaries. No-sky dimensions do not capture distant vertical sources.

Sky indexes are cached by column revision and shared across vertical jobs; an edit rebuilds the changed index while preserving independent indexes. A four-cube vertical regression now needs nine sky-index jobs instead of 36, plus four propagation jobs. Index construction computes terrain noise once per horizontal block column, shares candidate heights, and searches blocking edges top-down. Snapshot capture bulk-copies uniform section rows; generated fallback likewise evaluates noise once per X/Z. The solver copies intersecting cube rows instead of allocating and looking up a cube key for every cell, and only queues lit cells with a lower neighbor. Native emission, attenuation, face occlusion, the 15-block halo and stale-result checks are unchanged.

The neighboring-cube probe also exposed repeated invalidation while the old area unloaded after a vertical teleport. Sources remain in the manager through pending unload and leave only after saves acknowledge. If their captured revision still matches, retirement preserves ready views and the existing sky index, merges the sky summary into the cached saved foundation, and retains available detached block data in the bounded disk cache. A missing/stale capture still discards the foundation and invalidates dependent columns. Regressions verify both unchanged retirement (including a roof that must shade later rebuilds) and an unobserved edit immediately before unload.

Initial send selection now waits for current exact light; lighting targets include pending sends to avoid a dependency cycle. The first scoped exact packet installs its immutable light synchronously before the renderer can sample the newly installed cube. Subsequent replacements retain the queued lifecycle and the last accepted display during recalculation. No packet or disk format changes are needed.

Regression coverage includes the eight-job concurrency bound and batch publication, shared sky indexes and invalidation after a high roof edit, edit priority, exact generated fallback, native-engine parity, initial sender gating with ordinary columns still available, and immediate first-packet installation at both height signs. Initial generation and mesh scheduling remain separate bottlenecks; this work is not incremental block propagation or a guarantee of zero latency at arbitrary view distances.

## Client prediction of decreasing light (2026-10-29)

The single-cell hook now passes the previous block state. `ClientCubeLightPropagation` detects reduced emission, increased attenuation and newly occluding faces, then clears dependent block/sky values using the former block's outgoing faces. Its second queue refills from remaining emitters, unaffected neighbors and known direct sky. Torch removal leaves unrelated skylight intact; direct level-15 sky removal travels downward across loaded cube boundaries without attenuation. Newly opened faces seed their neighbors even if the edited cell's own light stays unchanged.

Both stages run against private copies on the client owner thread. Only the completed transaction becomes visible; temporary zeroes cannot reach rendering. The combined budget is **32,768 queue visits per edit**. If either stage exceeds it, the previous immutable display remains until server completion. ## Light-engine and network milestone

This section describes the earlier explicitly bounded mode. Normal gameplay now uses the automatic manager above; its scoped invalidation replaces the old whole-domain network lifecycle.

`CubeLightView` exposes immutable ranges from the current bounded publication. A cubic layer listener returns a scalar light value only when that cell's range is exact; otherwise it returns zero. It supplies a detached `DataLayer` only when all 4,096 values of that section and layer are exact. An incomplete cube may therefore expose useful exact cells or sections without being globally ready. Raw brightness combines the block and sky lower/upper bounds with sky darkening before deciding exactness, so an exact dominant layer can determine the result even when the other layer is uncertain. Constructor flags for disabled block or sky layers remain respected.

The server provider validates live holders on its owning thread. Off-thread engine reads return unavailable data, yielding zero scalar brightness or no section layer; they do not traverse mutable holder maps or wait on the server thread. The asynchronous query APIs below remain the way to dispatch a request from another thread. Client render workers read immutable cache publications checked against active cube identity and its volatile block revision. Ordinary worlds and the empty light engine retain their vanilla behavior. Cubic `lightOnInColumn` still returns false because one finite cube publication cannot establish readiness of a whole column.

Server block edits revoke stale publication data through the cube's revision hook. Queries and exports revalidate before use. On normal server ticks, the manager also checks changed holder membership, unloads, replacements, and newly loaded dependencies, then starts at most one replacement calculation for the last admitted area. Edits during a calculation are coalesced; a stale completion leaves a new attempt for a later tick rather than recursively starting work. Revocation covers the complete domain of up to 27 cubes. Unchanged empty and uncertain domains remain idle, and neither reads nor block setters start workers.

The full-cube payload now has outer wire format **4**. It contains the canonical cube position, a nonnegative lighting epoch, full block/heightmap/block-entity data, and an optional complete `CubeLightView`. Light is included only when every block and sky value in that cube is exact. Each layer contains exactly eight 2,048-byte section arrays in cube XYZ section order: 32 KiB of light values in total, plus framing. Strict presence, section-count, array-length, version, epoch, and position checks prevent partial or mismatched fields from being treated as complete light. An absent light payload means unavailable, not a known all-zero field. Blocks, block entities, and exported light are captured together on the owning server thread. There is no standalone packet that installs light independently of block data.

A separate invalidation payload advances a monotonically increasing server-world lighting epoch and clears the client's old publication. It is sent before full snapshots carrying that epoch; equality is accepted for the replacement snapshots. Initial sends and publication broadcasts export only current data for the exact active cube instance. Previously delivered light is revoked when its dependencies change. This uses custom cube payloads rather than vanilla vertical-column light masks.

An observer or transport exception does not turn a valid calculation into a failed result. The manager retains the latest notification epoch and a union of at most 54 old/new cube positions, retrying notification after 20 ticks without rerunning the solver. A different domain cannot be admitted while a notification remains pending. Repeated sends retain invalidation-before-snapshot ordering; status exposes notification failure separately from computation failure.

On the client, full blocks are installed first and their temporary buffer is released. The queued light callback checks the current world, cached cube identity, post-install block revision, server epoch, and local cache generation before applying light. Full replacement clears that cube's previous view. Accepted complete light marks the transient light cache ready; application and invalidation dirty all eight cube sections and their neighbors. Geometry readiness now depends on loaded block cubes, so unknown light does not block initial entry. Neither readiness flag changes `isLightCorrect`.

Ordinary block deltas and client prediction conservatively invalidate all cached light views, including when the edited cube lies outside the server's bounded publication, and require a newer server epoch. Cache loss has a different contract: drop, ring-slot eviction, and view-radius loss clear cached light and advance the callback generation without revoking the server epoch. Old queued callbacks cannot restore it, but a fresh full snapshot from the same epoch can. A same-position full replacement also checks its new local revision, since it may reuse the existing `LevelCube` object.

The client retains at most one cached cube position as a recovery anchor after local invalidation or cache loss. A full packet carrying complete light also registers an anchor after installing its blocks and before queuing the light callback. This permits recovery when the first queued callback is rejected after an intervening edit, without exposing its light early or resetting an existing retry timer. A packet without light does not register this expectation. The client may send five requests at cumulative eligible client ticks 20, 60, 140, 300, and 500. Polling requires the current cubic world, a live connection, and support for the recovery payload; receiving ready light cancels the request, and a missing anchor or the attempt limit stops further sends. Recovery can give up if the server never has exact current data.

The serverbound recovery payload uses wire format **1**, containing a cube position and the observed lighting epoch. The server checks the current player, world membership, cube tracking, coordinate validity, and that the epoch is nonnegative and not in the future. It accepts at most one successful recovery per 20 normal lighting ticks for the whole world. A successful request republishes existing complete views at a newer epoch; it cannot select bounds, create holders, load cubes, or start a solver. Invalid or unready requests do not consume that successful-recovery budget. Recovery uses the current full-cube format and does not change disk formats.

These engine and packet paths do not set `isLightCorrect` or write lighting to disk. Disk formats 1/2 remain unlit, production solves still use `CubeLightBoundary.UNKNOWN`, and a verified open-sky boundary remains missing. Without that proof, a clear bounded column cannot become a sky source. Only the current bounded publication is exposed; there is no automatic world-wide lighting scheduler.

## Bounded light propagation milestone

`BoundedCubeLightSolver` computes both block and sky light through a finite 3D domain. `CubeLightBlockSnapshot` copies every block state in each supplied cube, so the worker does not read live sections or holders. Block emission seeds the block-light field. Transfers use the destination state's `getLightDampening()` and the opposing face-occlusion shapes of both blocks. Ordinary transfers lose at least one light level; direct level-15 sky light moving downward through an unoccluded edge into a zero-dampening block remains level 15. These rules apply across cube boundaries as well as inside sections.

The solver computes separate lower and upper fields, each in the range 0–15. Missing cubes and unknown exterior inputs contribute no assumed incoming light to the lower field and the maximum possible incoming light to the upper field, subject to the known destination's dampening and face. Missing cubes remain unsampled; they are not installed as air. A `LightRange` is ready only when its lower and upper values agree, and `exactValue()` is empty otherwise. `CubeLightSolution` also reports readiness for all cells of a cube, per layer or for both layers. This describes the detached calculation, not global world or client readiness.

`CubeLightBounds` accepts inclusive cube corners and rejects unsupported coordinates, reversed bounds, more than 27 cubes, or more than 1,048,576 cells before allocating voxel data. The detached solver accepts explicit exterior boundary observations, but the production manager always uses `CubeLightBoundary.UNKNOWN`. There is no verified open-sky source wired into the server path yet. Explicit exterior inputs cannot fill a missing cube inside the domain.

The asynchronous server-level, cube-cache, and chunk-map bridges expose:

- `cc_rebuildCubeLighting(bounds)`: capture loaded FULL cubes on the owning server thread, compute on a worker, then publish on the server thread. Its future returns `PUBLISHED` or `STALE`; invalid input, a busy manager, closure, and computation or dispatch failures fail the future.
- `cc_queryCubeLight(layer, blockPos)`: validate the current publication and return `CURRENT` with a light range, `STALE` without a range, or `UNAVAILABLE` without a range. A current but unequal range is still uncertain. Missing cubes and positions outside the published bounds have no sample.
- `cc_getCubeLightStatus()`: report the selected bounds, phase (`IDLE`, `RUNNING`, `CURRENT`, `DIRTY`, `RETRY_WAIT`, `FAILED`, or `CLOSED`), consecutive calculation failures, retry delay, and last failure. Pending notification and its failure are reported separately; a current publication can coexist with a delayed notification.

These APIs dispatch off-thread calls to the owning server thread; callers must await them asynchronously rather than blocking that thread. Unlike the historical surface and skylight-obstacle queries below, capture uses only FULL cubes in `updatingChunkMap`. Saved files, provisional cubes, and `pendingUnloads` do not establish current lighting coverage. Imposters resolve to their wrapped full cube.

`CubeLightManager` retains at most one active calculation and one publication, plus the last admitted bounds and their dependency watch even when no publication exists. Every position records availability, holder identity, cube identity, status, and a lighting revision. Block setters and bulk section replacement advance that revision; captures and saves do not. Previously absent cubes becoming available can therefore trigger an automatic refresh even after an empty calculation. Saved or pending-unload cubes remain unavailable to this path.

An explicit request's future describes one attempt, not the lifetime of automatic maintenance. Busy requests and failures before successful input capture do not retarget the selected area. Once capture admits an area, later worker, computation, or dispatch failures leave it selected for bounded retry. Calculation failures wait 20, 40, 80, then 160 ticks between attempts and pause after the fifth consecutive failure. A dependency change or an explicit rebuild can resume work. Closing clears the selected area, fails an outstanding future, and prevents late completion or automatic retry from publishing.

Automatic maintenance runs from the normal no-argument cube-map tick; task polling and unload/shutdown drains alone do not advance it. Every attempt recalculates the finite domain from fresh snapshots. Selecting areas across the world, incremental propagation, and updates across independently managed domains remain future work. The engine and network bridges consume validated immutable views rather than populating vanilla's column-light storage. `isLightCorrect` is not set, disk formats 1/2 remain unlit, and unknown values retain the unavailable/zero fallback.

## Skylight occlusion milestone

Minecraft 26.3's direct-skylight source boundary is an edge between an upper and lower block. The edge blocks unattenuated sky when the lower state's `getLightDampening()` is nonzero, or when the upper downward face and lower upward face occlude together. This differs from the six ordinary heightmap predicates. Water, leaves, slabs, and other partial shapes therefore require the actual lighting rule. A reported boundary Y is the upper block's Y, rather than an opaque block's Y.

`CubeSkyOcclusion` captures all 1,024 horizontal columns of a 32-block cube. It stores the highest internal blocking edge and detached top/bottom block-state planes. It does not assume air outside the cube. `CubeAccess` caches this immutable snapshot; ordinary block edits and bulk section replacement invalidate it. The next query rebuilds the cube's summary. Proto-to-full conversion starts with a fresh cache, and imposters delegate to their wrapped full cube. `initializeLightSources` and the generation `INITIALIZE_LIGHT` stage now prepare this data without claiming `isLightCorrect`.

`cc_querySkyLightColumn(blockX, blockZ, minCubeY, maxCubeY)` combines request-time live snapshots with persisted section data, using the existing FIFO disk scan and its limits. It returns `KNOWN_BLOCKING_EDGE`, `CLEAR_WITHIN_RANGE`, or `UNKNOWN`. Only edges with both endpoints inside the inclusive whole-cube range are examined. Adjacent FULL snapshots supply both faces for a boundary check. Missing and provisional cubes remain unknown; unknown coverage above a known candidate prevents claiming that candidate is the highest boundary. Gaps below the winning edge do not change it.

`CLEAR_WITHIN_RANGE` and `isComplete()` describe only that bounded observation. Neither establishes that skylight enters from above the range, sets a brightness value, nor replaces `canSeeSky`. Finding the highest direct-sky boundary also does not compute attenuated light or light arriving from neighboring columns. The separate bounded propagation kernel above can represent uncertain incoming light, but the server still needs verified sky inputs before it can claim open-sky illumination.

Persisted occlusion summaries are rebuilt from authoritative section palettes in formats 1 and 2. This reconstruction needs no new disk field, second persisted index, or neighbor-dependent verdict stored in a cube file. It also lets unloaded neighboring cubes contribute after reopening. Queries do not instantiate entities, attach holders, or rewrite files. The current scan, palette decoding, and whole-cube summary rebuild are correctness-oriented; an efficient lighting engine will need change tracking and reuse.

The old cubic light mixin returned maximum raw brightness and reported enabled columns. Its replacement reads exact computed values from the bounded provider, with zero or absent section data for uncertainty and disabled column readiness. It does not infer open sky from a missing publication. Ordinary worlds keep their original listeners and brightness behavior. The vanilla `ChunkSkyLightSources` getter remains unsupported for cubes because it assumes a 16×16 column and an external air boundary; the new 32×32 bounded snapshot cannot satisfy that contract.

Global `Level.getHeight` remains unmodified. Its consumers can mutate weather, spawn entities, and inspect regions outside a requested interval, so a historical bounded answer cannot safely stand in for current world-wide height. Generation also consumes proto cubes before FULL status; making it await the FULL-only server query would create a dependency cycle. A future cubic generation region must use its already-acquired dependencies and explicit bounds, while skylight integration needs its own unknown-coverage policy.

## Column-surface milestone

`cc_queryColumnSurface(type, blockX, blockZ, minCubeY, maxCubeY)` queries a vertical interval with inclusive whole-cube Y bounds. Its `ColumnSurfaceResult` distinguishes `KNOWN_HEIGHT`, `KNOWN_EMPTY`, and `UNKNOWN`. Only FULL cubes establish coverage. Missing files and cubes still in generation remain unknown, even if their current local maps are empty. For an unknown result, the API exposes the highest unknown cube and, when available, the highest matching block already observed below it. A known surface needs coverage above that block; holes below it cannot change the answer. Empty local maps contribute coverage without inventing a block at `cubeMinY - 1`.

On the server thread, the query captures detached local maps from live holders, including cubes awaiting unload. Active holders take precedence over pending holders; their maps override saved observations, including when a top block was removed. Calls from other threads are dispatched to the server thread before capture. The query then queues one disk scan in the same FIFO stream as cube writes and deletes, and merges the results on the server thread. Its result describes the request snapshot, not later edits made before the future completes. Callers must await it asynchronously rather than blocking the server thread.

`ColumnSurfaceIndex` uses a sparse sorted map, so querying a large missing interval does not iterate through every possible cube Y. The disk scan reads matching existing files without loading them into the world's holder map. Format 2 supplies validated local maps; format 1 reconstructs them from section palettes without invoking entity, structure, or tick loading. A query does not rewrite those files. Cube blocks and local maps already share an atomic file replacement, so this milestone uses no secondary persisted index and no cache that can diverge from them.

Malformed encountered storage names, corrupt selected NBT, incompatible formats, inaccessible selected paths, and symlinks fail the query instead of yielding partial coverage. A scan is capped at 16,384 matching cube files, 64 MiB of decoded NBT accounting per cube, 128 MiB in aggregate, and 1,000,000 enumerated directory entries. Exceeding a limit also fails the whole query. The scan enumerates the storage root and selected region directories; it cannot discover a cube incorrectly placed in an unrelated region. A missing observation remains unknown. These scans and the subsequent server-thread parsing are a correctness baseline, not a performant per-block lighting lookup.

`Level.getHeight` still follows the vanilla column path. Connecting generation and skylight requires an explicit policy for unknown coverage, efficient surface-change tracking, and integration with lighting propagation. The reviewed Core tree storage is not used; see [REFERENCE_REUSE.md](REFERENCE_REUSE.md).

## Local heightmap milestone

`CubeHeightmap` covers the cube's entire horizontal footprint. At the current 32-block diameter, each of the six vanilla heightmap types has 1,024 columns. It stores local first-available offsets from 0 through 32 in six bits per entry, using 103 packed longs per map. Offset 0 means no matching block inside this cube; highest-taken queries return `cubeMinY - 1` for that case. A matching block at the cube's top produces a first-available height of `cubeMinY + 32`. Queries expose absolute Y, including negative and extreme supported cube coordinates.

This is a new local packed-map implementation using Minecraft 26.3's `Heightmap.Types.isOpaque()` predicates for air, fluids, leaves, and motion-blocking tags. It does not wire in Core's surface tracker tree. Queries prime caches lazily; block edits through `ProtoCube` and `LevelCube` update existing maps and dirty state. Bulk section replacement invalidates the caches. Code that mutates sections directly must invalidate heightmaps explicitly. Proto-to-full conversion copies map arrays rather than sharing mutable caches, and the shared heightmap interface bridges vanilla columns and cube imposters.

Cube block-packet data carries all six maps with its inner format version 2, followed by the complete block-entity snapshot. It validates packed lengths, offsets, and unused bits before application; packet snapshots and exposed map arrays are detached. The containing full-cube packet now uses outer format 4 with its optional exact light and epoch. These wire versions are separate from the disk format below and require matching client/server code.

These maps describe cube-local surfaces. The bounded column query above aggregates them across loaded and unloaded cubes, but global world-height integration and skylight remain unfinished.

## Cube persistence milestone

`SerializableCubeData` captures an immutable NBT snapshot on the owning game thread. New files use identifier `cubicchunks:cube`, `CubeFormat=2`, the configured cube diameter, and the exact current Minecraft `DataVersion`. Format 2 requires a `CubeHeightmaps` compound containing all six named maps, with strict packed-length, offset-range, and padding validation. Loading also checks all three coordinates, the packed coordinate range, status, section indices, registry IDs, and supported NBT fields.

The loader still accepts this branch's format 1 schema, which had no heightmap field, and reconstructs its derived local maps from the saved sections. Loading alone neither rewrites the file nor marks its blocks dirty; the next ordinary snapshot writes format 2. Both versions require the exact current Minecraft data version. This local format migration does not use vanilla chunk data fixing and is not an importer for older Cubic Chunks or RegionLib `.3dr` worlds.

For the current 32-block cube size, the snapshot preserves:

- Block-state and biome palettes for all eight sections, using the Minecraft 26.3 codecs.
- All six local heightmaps, covering every horizontal column of the cube.
- Generation status, inhabited time, and pending postprocessing offsets.
- Block-entity NBT and inventories, including pending tags when a FULL cube is saved before its post-load callback runs.
- Proto-cube entity NBT, including passenger data. Live entities in FULL cubes use the separate `cube_entities` lifecycle described below.
- Scheduled block and fluid ticks, including relative delays and priorities.
- Structure starts and references.

`CubeStorage` stores compressed NBT at `cubes/r.<regionX>.<regionY>.<regionZ>/c.<x>.<y>.<z>.nbt`, alongside vanilla `region` storage. Each region directory covers 32 cubes per axis; it is not a packed region file. Writes run in order on one I/O worker, compress and validate the exact output bytes in memory against the read limit, write those bytes through a file channel, force its contents, and atomically replace the destination. Unsupported atomic replacement fails rather than falling back to a partial overwrite. The parent directory is not fsynced, so file forcing and atomic replacement do not guarantee directory-entry durability after sudden power loss on every filesystem. Only a missing file produces an empty cube; corruption, incompatible metadata, and I/O errors remain load failures.

Autosave captures a detached snapshot on the owner thread and queues disk work without waiting. A pending snapshot never clears changes made after capture; failed acknowledgement restores dirty state, retains unloading holders, and makes subsequent flush/close fail. A proto cube cannot overwrite an existing FULL cube: the check and replacement run as one ordered worker operation. Normal unload retries on later ticks until terrain, POI and entity writes are acknowledged. Explicit flush and shutdown still wait. Per-cube files create many filesystem entries; packed-region storage and large-world throughput remain future work.

Cache, level, and server shutdown also close storage after a save failure. Tests invoke the actual `MinecraftServer.stopServer` path and verify that the original save error survives, cleanup errors are retained as suppressed exceptions, and the cube storage lock can be reacquired afterward. This cleanup releases resources; it does not turn a failed save into a successful one.

The serializer supports unlit cube state only: it rejects initialized lighting, upgrade data, blending data, and below-zero retrogen instead of dropping them. Its local maps now support bounded column queries; lighting persistence remains unfinished. Cubic-world initialization remains rejected outside tests, and `general.generateNewWorldsAsCC` remains `false` by default.

The reference review is documented in [REFERENCE_REUSE.md](REFERENCE_REUSE.md). CC2's `RegionCubeIO`, `CubeSerializer`, and `AsyncSaveData` are byte-identical to the existing `src_old` copies. Their field checklist informs this implementation, while the new code uses 26.3 APIs and explicit version/error handling. The older sparse heightmap, unloaded-neighbor lighting, and surface-change algorithms provide useful starting points for later milestones.

## Cube broadcasting and send readiness

Cube holders allocate exactly eight changed-block section slots, including in dimensions whose vanilla height has fewer than eight sections. The vanilla constructor keeps its own dimension's section count. Cube broadcasting captures current states directly from the cube and sends custom `cube_block_changes` packets for both single and batched changes. Unwatched sections are drained, completed sections are cleared, and a transport exception retains the failing section for retry; recipients that already received part of that section may receive it again.

The copied vanilla light-mask branch and its nonexistent `ClientboundLightUpdatePacket(CubePos, ...)` constructor are removed. Cube light still uses `CubeLightManager`'s validated full-cube publications and invalidation packets. No vanilla column light packet is constructed for a cube. `sectionLightChanged` continues to reject column-style light-mask input for cube holders.

When a CLO becomes ready to send, its position is checked against each player's 3D tracking view before queuing it, and the chunk cache is notified as in vanilla. Ordinary column objects retain `LevelDebugSynchronizers.registerChunk`. Cubes do not enter that column-keyed debug subscription store, so they cannot overwrite another cube's registration at the same X/Z. Cube debug overlays still require a separate protocol and lifecycle.

The version-1 `cube_block_changes` format carries a canonical 21-bit-per-axis cube position, an XYZ section index 0–7, and 1–4,096 distinct section-local block positions with registered block-state IDs. World block or section positions are never packed into vanilla position longs in this wire format. Tests cover the full supported block-Y range, -33,554,432 through 33,554,431. Version, coordinate aliases, section/count/local-position bounds, duplicate entries, unknown registry IDs, presence flags, and truncated data are checked before client mutation.

An entry may include a registered block-entity type and detached NBT from its normal `ClientboundBlockEntityDataPacket`. Save-only data is not requested. The type must support the changed state. Each encoded update tag is capped at 64 KiB and parsed with a 2 MiB allocation limit; a packet holds at most 256 KiB of tag bytes. Large sections stream multiple bounded packets, with block states and their own tags kept together. Oversized individual tags and unsupported custom block-entity packet classes fail capture and retain dirty changes instead of dropping data. These limits are development-protocol limits, not support for every mod's custom packets.

The client handler checks the current cubic world and finds the exact already loaded cube without creating one. If the block has an outstanding prediction, its authoritative state and block-entity tag are retained together until acknowledgement. Otherwise it applies the state directly to that cube, then loads matching block-entity data using the 26.3 component-aware input API. It updates local heightmaps and section emptiness through the normal cube setter and notifies rendering; NBT-only changes also notify rendering. Changed blocks revoke old light, while duplicate states preserve the matching light snapshot. Missing, dropped, and previous-world cubes are ignored.

## Player actions and prediction at extended heights

The version-1 `cube_player_action` and `cube_use_item_on` payloads carry three full signed integer coordinates, bounded to the cube-key range on every axis. The first accepts only start, change-direction, stop, and abort block-destruction actions. The second carries a validated face, hand, finite double-precision hit offsets, strict inside/border flags, and the original sequence. Both reject negative sequences, bad versions, invalid enum values, out-of-range coordinates, and truncation. Positionless actions, including ordinary item use, keep their vanilla packets and share the same sequence generator. The client converts packets in its play listener before wire encoding, including non-predictive abort/direction changes; a missing custom channel fails instead of falling back to a truncated position.

Fabric dispatches received actions on the server thread. A receiver requires a loaded client in a cubic world and a tracked, already loaded FULL target cube. Use-on-block also requires an available in-range adjacent cube. Unavailable targets are acknowledged without loading or generating cubes so the client can discard the prediction. Available actions reconstruct vanilla packet objects in memory and enter the original server listener and game-mode methods. Reach, hit-distance, enabled-item, spawn-protection, interaction permission, game-mode restriction, and pending-teleport checks remain in those methods. Only the height bounds used by the action listener are replaced with the cube range. This is not an alternative permission implementation.

Vanilla direct `ClientboundBlockUpdatePacket` sends in cubic play connections are converted before encoding to the existing cubic delta payload. When a matching full cube is loaded, corrections include its normal block-entity update tag; otherwise the supplied authoritative state is retained. An adjacent correction outside the supported cube range is discarded. Ordinary-world corrections and sequence acknowledgements retain vanilla packets. This closes the response path used by denied destruction and use-on-block, in addition to the regular holder broadcasts.

`ClientCubePredictions` belongs to one client level and uses immutable `BlockPos` keys rather than packed longs. The existing `BlockStatePredictionHandler` still owns prediction scopes, sequence numbers, and teleport sequence markers. Successful predicted edits retain the original state, visible block-entity update data, player position, and loaded cube identity. Repeated edits advance the pending sequence while preserving the oldest baseline; authoritative updates replace the retained state/tag pair. Cumulative acknowledgements reconcile only entries at or below that sequence, using the loaded cube directly. A changed collision state can restore the player's earlier position under the same teleport-sequence condition as vanilla. Removal, eviction and radius loss discard affected predictions; a late acknowledgement cannot modify a replacement cube. Full relight packet handling preserves and replays pending states on the same resident cube while replacing their authoritative baseline. Raw cache replacement still clears pending entries, with replay managed by the packet handler. No prediction path creates a missing cube.

Level build-height predicates now use the supported cubic block range while dimension min/max metadata and section-array counts remain unchanged. Ordinary levels retain their original predicates. Block access also rejects unrepresentable X/Z coordinates, avoiding cube-key aliases. Other world-height consumers, collision/simulation limits, other specialized packets, debug networking, and complete rendering at extended heights remain unfinished. These tests do not establish a live multiplayer session or arbitrary-height gameplay.

## Full cube block-entity snapshots

`CubeBlockEntitySnapshot` scans all eight sections for block states with block entities. Capture resolves each instance with `EntityCreationType.IMMEDIATE`, promoting pending saved NBT or creating a missing runtime instance, then checks its position and block-state compatibility. Each entry contains a registered type and a detached `getUpdateTag` result. This is the vanilla initial client synchronization contract, distinct from `getUpdatePacket` and from saved inventory NBT. Entities with empty initial tags or no change packet are included; chest contents remain synchronized through menus.

The 15-bit cube-local position combines a three-bit XYZ section index with a twelve-bit section-relative position. Decoding combines it with the canonical cube key, preserving the supported block-Y range -33,554,432 through 33,554,431. Counts, local positions, duplicate entries, type IDs, NBT, and byte budgets are validated. Snapshots allow at most 32,768 entities, 64 KiB per encoded tag with 2 MiB NBT allocation accounting, and 512 KiB for the whole entity body including framing. Section data is capped at 256 KiB. Together with all six heightmaps and at most 32 KiB of light, the full packet remains below the vanilla 1 MiB custom-payload limit. Oversized snapshots fail capture as a whole; they are not split and entities are not silently omitted. These are development-protocol limits, not support for every mod's initial tags.

Before changing a cached cube's block/entity contents, the client reads fresh sections, rejects truncated or trailing section data, validates entity positions/types against those sections, and creates and loads fresh block entities using the 26.3 component-aware NBT API. Only after preparation succeeds does it clear the old objects, tickers, and pending tags, install the sections and heightmaps, and register the new entities. This preflight protects the previous snapshot from malformed section data and incompatible entity types; it does not promise transactional recovery from arbitrary mod callbacks during registration. Repeated snapshots also replace same-type instances, removing fields absent from the new initial data. Cache drop, ring eviction, and view-radius loss perform the same entity cleanup.

The handler accepts only the current cubic client world and an in-view cube. Entity installation completes before light is queued. Existing epoch, revision, cube-identity, and cache-generation checks prevent older queued light from restoring a replaced snapshot. Prediction entries are discarded after a successful full replacement; rejected section/entity data does not discard them. Packet data is detached, including read-only section buffers and fresh decoded NBT for each consumer. Outer wire format 4 and inner format 2 reject older versions; both ends need the updated mod. Disk format 2 and its format-1 migration are unchanged.

## Editing block entities at extended heights

Five new version-1 payloads use signed integer XYZ positions bounded to the supported cube range: serverbound `cube_sign_update`, `cube_set_command_block`, and `cube_set_structure_block`, plus clientbound `cube_open_sign_editor` and `cube_block_entity_data`. The play listener converts the three vanilla editing packets before serialization only in cubic worlds and rejects a missing custom channel. Ordinary worlds keep their vanilla packets. The common server send hook preserves direct sign-editor opening and the exact directed block-entity tag; it does not substitute a normal broadcast tag for the command editor's `saveCustomOnly` response. These responses retain their original recipient.

Sign data contains exactly four lines, each at most 384 characters, plus a validated front/back slot. Command data retains its mode and all three flags. Structure data retains the update operation, mode, name, offset, size, mirror, rotation, metadata, all four flags, integrity, and seed. Offsets and sizes retain the vanilla 48-block limits, metadata is capped at 128 characters, and integrity must be finite and within 0–1. Malformed versions, positions, enum values, flags, bounds, and truncated fields fail decoding; mutable positions, vectors, and lists are detached. Command text and structure name/metadata have an additional combined 32,000-byte UTF-8 budget, leaving room for framing below the 32,767-byte serverbound custom-payload limit. Oversized text fails explicitly without truncation or fragmentation. Directed entity NBT uses the existing 64 KiB encoded-tag / 2 MiB allocation limits.

Editing requires a loaded client in a cubic world and a tracked, already loaded FULL target cube. Command and structure envelopes reconstruct vanilla packet objects in memory and enter the original server listener, preserving `canUseGameMasterBlocks` checks, command settings, operation selection, and feedback. The command mode-change path replaces its column lookup and entity reinsertion with the target cube; it does not load a column. Target validation does not establish that every cube later visited by a structure operation is loaded.

Sign updates strip formatting and use the player's normal asynchronous text filter. The result is applied on the captured server executor only if the original world, connection, tracked cube instance, and sign instance remain current. The original sign method still checks editor UUID and wax state, applies the player's filtering preference, clears editing ownership, and sends block updates. This path bypasses vanilla's column-only `hasChunkAt` check. On the client, both response handlers require the current cubic world and an already instantiated entity in a loaded cube. Directed data checks the type, uses component-aware NBT loading, notifies rendering, and refreshes an open command editor as vanilla does; missing, dropped, wrong-type, and previous-world targets are ignored.

The editing milestone covers transport, settings, and dispatch; the sections below supply cubic size detection and block-template capture/placement. Command execution/ticking at extended heights, other specialized packets (such as jigsaw/test/debug operations), and visual editor behavior still require integration work. Existing full-cube wire versions (outer 3 / inner 2) and disk format 2 remain unchanged; client and server need builds with the editing channels.

## Structure corner detection at extended heights

`MixinStructureBlockEntity` replaces only the cubic `getEnclosingBoundingBox` search. The original `detectSize` method keeps its SAVE-mode gate, interior-size calculation, rejection of degenerate dimensions, dirty marking, and block update notification. Non-cubic levels retain the original column-based search.

`CubeStructureCorners` searches the inclusive box from controller minus 80 through controller plus 80 on X, Y, and Z. The vertical radius is a deliberate cubic-world rule: the scan follows the controller's height and has finite cost without dimension min/max metadata or an unbounded vertical walk. Bounds are clipped to the supported block range on every axis. At most 216 cubes intersect this area; near the simultaneous coordinate limits only 27 are needed. Out-of-range origins are rejected before any lookup. Corners outside the box are excluded even if their cube intersects it.

The owning-thread search first obtains the entire area with `cc_getCubeNow`, verifying each cube's position and owning level. It neither requests generation nor waits on pending cube futures. Any missing or mismatched cube fails the whole search, leaving the controller's existing offset and dimensions intact. The normal structure-size failure feedback applies; loading the area and repeating detection can then succeed. This requirement is for the entire search box, not just the cubes containing known corners.

After coverage is established, the search uses palette predicates to scan structure blocks in all eight sections of each cube. It resolves block entities directly from their cube, including pending saved NBT, and counts only CORNER entities with the same normalized structure name. Stale entity-map entries without a structure block do not count. As in vanilla, one matching corner uses the SAVE block as the other bound; two or more corners bound themselves and do not automatically include the controller. Null names retain vanilla equality semantics, although the normal edit handler requires a valid name before invoking detection. No world position is packed into a vanilla block-position long.

The existing `SCAN_AREA` editing packet invokes this real search and its block-entity update carries the resulting offset and size back to the client. Packet and disk versions do not change. It does not search through unloaded disk data or establish playable cubic worlds.

## Structure template capture and placement at extended heights

Minecraft 26.3's `StructureTemplate.fillFromWorld` uses the column-based `Level.findBlocksIn` scanner. `MixinStructureTemplate` substitutes `CubeTemplateBlockMatcher` only for cubic levels. It reads the requested XYZ box from ready FULL cubes, including air and all intersected sections. Vanilla retains the ignored-block filter (including `structure_void`), relative coordinates, palette ordering, component-aware block-entity serialization, and template manager/file format. Pending block-entity NBT is promoted through the existing cube-backed level access. Ordinary worlds still use their original scanner.

`CubeTemplateArea` resolves the entire finite source box through `cc_getCubeNow`, checking cube coordinates and owning level before any template changes or pending-tag promotion. Missing/wrong coverage, nonpositive sizes, or coordinates outside the supported block range make structure-block SAVE return false before touching the manager, cached template, or file. Direct `fillFromWorld` callers receive `IllegalStateException` for an unsupported area rather than silently retaining an old palette. Positive dimensions are checked against the coordinate span before arithmetic, avoiding integer overflow; this does not impose the editor packet's 48-block limit on API/corner-derived sizes.

Placement on cubic `Level` instances preflights the vanilla transformed bounding box, including mirror, rotation, and pivot, before palette selection, processors, random consumption, barrier placement, or block writes. Shape repair or waterlogging adds one block of required coverage on every side. The whole box is required even when a placement bounding box or integrity processor would discard some blocks. This conservative check rejects missing cubes and an unrepresentable border, without requesting generation or waiting for futures. Default placement therefore needs one block of space inside the supported coordinate endpoints; API calls with both known shape and ignored waterlogging may place directly at an endpoint. Capture itself can include endpoint blocks.

The original placement code still handles state transforms, barriers before block-entity replacement, inventories/components, integrity, bounding-box clipping, waterlogging, neighbor shape repair, and dirty marking. Structure-block LOAD retains the vanilla size-confirmation step; if sizes already match but coverage is missing, it returns false instead of claiming success. The existing vanilla LOAD preparation feedback is used, and the operation can be retried after coverage is ready. No automatic retry or new wire/disk version is introduced.

The next section extends this block and block-entity path with resident entities. This does not implement world-generation accessor integration, arbitrary third-party processors that move blocks outside template bounds, transactional rollback of block callbacks, or guarantees about subsequent ticking/neighbor cascades. Disk I/O failure handling remains vanilla.

## Resident entities in structure templates

`CubeTemplateEntities` enumerates the actual server entity manager's resident sections and filters entities using full XYZ bounding boxes. It does not use the packed section-Y range query, which aliases at large heights, or the column visibility flag to exclude otherwise resident entities. Movement and removal are reflected through the existing manager callbacks; there is no parallel entity-only store. Capture is linear in the number of resident entities. This is a snapshot of entities already in memory, not a request to load entity data from disk; loaded block cubes alone do not establish that pending entity data has arrived.

The snapshot excludes players, removed entities, entities belonging to another level, and types that cannot serialize. It uses bounding-box intersection with the selected area. A selected vehicle and its selected passengers form one NBT tree; passengers are not duplicated as root entries. If a vehicle is outside the selection, its selected passenger becomes a root. Unselected passengers are omitted. Vanilla entity serialization retains ordinary state, names, health, equipment, and components. The standard `entities`, `pos`, `blockPos`, `nbt`, and `Passengers` fields are used; nested saved positions remain absolute, and placement derives their offsets from the saved root position. Block-attached entities use their actual attachment anchor. No template, cube-disk, or packet version changes.

Entity capture completes before replacing template palettes. A snapshot permits at most 1024 selected entities and at most 32 levels in a passenger tree; the native serialization traversal, including descendants later pruned, has the same bounds. Oversized capture returns false through the structure-block SAVE entry point and preserves an existing cached template and file. Direct template API callers receive `InvalidSnapshotException`. These bounds also apply while preparing entities from an imported template.

With `ignoreEntities=false`, placement prepares all selected roots and passengers before block writes: transform fractional positions and anchors with the requested mirror/rotation/pivot, remove every entity UUID, deserialize native entity instances, restore passenger links, and verify supported coordinates and ready cubes for every resulting bounding box. Unknown types, invalid coordinates, excessive nesting/count, attachment failures, or missing coverage reject placement. Bounding-box clipping uses the transformed root anchor, as in vanilla. Large entities can need more cubes than the block template and its border. `ignoreEntities=true` skips both entity capture and preparation.

`MixinEntity` replaces the three position clamps in `Entity.load` only in cubic levels, allowing the supported coordinate span before subclass NBT validates anchors. Non-cubic levels retain the original clamps, including Y ±20,000,000. Block-attached entities rebuild their specialized bounding box from the transformed anchor; using a painting's visual center with `snapTo` would move an even-sized painting's anchor. Ordinary entities retain vanilla yaw/pitch transformation. After block placement, native spawn finalization runs when requested and `tryAddFreshEntityWithPassengers` registers roots and passengers through the server manager's UUID checks and callbacks. Repeated pastes receive distinct UUIDs without changing template NBT.

Structure-block LOAD now propagates the actual template placement result while retaining the vanilla size-confirmation step. Preparation failures therefore cannot produce a successful LOAD result. A later registration rejection is reported as false, but this is not a transactional rollback of already placed blocks, entities, or callback effects. Arbitrary cross-entity references such as leash owners and brain memories are not remapped. Cube entity persistence, visibility, ticking, and navigation are described below; they do not replace the manager's packed section index globally. Hanging-entity survival behavior and end-to-end multiplayer still need validation.

## Live entity persistence in cubes

`CubeEntityPersistence` is configured on the native `PersistentEntitySectionManager` immediately after its construction in `ServerLevel`. It is active only for cubic levels and opens storage lazily in the dimension's `cube_entities` directory. Ordinary levels keep native entity regions and lifecycle methods. Cubic manager autosave, save-all, and close now use this coordinator; vanilla column status updates, queued loads, and column unloads are disabled for those managers so they cannot read or write a second copy or unload other heights. The constructor hook targets the field assignment only, before the chunk cache is constructed.

The cube status listener loads entities when a cube becomes accessible (FULL or higher). Repeated status changes do not load it twice. `cc_areCubeEntitiesLoaded(CubePos)` reports completion independently from block availability. When the real `ChunkMap` releases a FULL cube, it first saves blocks and entities, then removes entity objects/UUIDs and the block holder. A failed entity operation retains the holder and live entities and propagates through the existing cube-save failure path. Changing status to INACCESSIBLE alone does not unload entities prematurely. Save-all and shutdown are connected through the native manager entry points; both native and cube stores close even when a save fails.

The new entity format is separate from block cube format 2: `Format=cubicchunks:entities`, `EntityFormat=1`, exact Minecraft `DataVersion`, a three-integer `Position`, and an `Entities` list of native entity NBT trees. Files use `cube_entities/r.X.Y.Z/c.X.Y.Z.nbt`, with the same atomic file replacement, ordered I/O, accounting limits, and exclusive directory lock as `CubeStorage`. There is no import of vanilla entity regions or older Cubic Chunks files, and mismatched versions are rejected rather than data-fixed or overwritten. Existing block, template, and packet versions are unchanged.

Persistence groups resident roots by their actual full block coordinates, without using the vanilla packed section Y. UUIDs stay unchanged. Native state includes fractional positions, motion, names, health, equipment/components, and attachment anchors. A passenger tree belongs entirely to its root's cube even when passengers occupy another cube. Passenger positions are written explicitly instead of inheriting their vehicle's X/Z; the loader validates the complete tree and restores riding links. Players and non-serializable roots are excluded. Native `shouldBeSaved` ownership rules, including player-owned vehicles, remain; unloading never removes players and retains trees with player passengers. The prior cubic `Entity.load` clamp fix applies before subclass anchor validation.

Before saving, all resident root destinations are loaded and merged with their saved entities. This prevents a fresh spawn from overwriting an entity file that has not yet been requested. All previously loaded cubes participate in the snapshot, including empty old cubes after movement, death, boarding, or dismounting. Every snapshot is prepared before any write. Loading validates format, owner coordinates, finite supported positions, UUID uniqueness, and passenger structure before manager registration; unknown roots/descendants or UUID conflicts with a resident entity fail the operation. The limits are 16,384 entities per cube snapshot and 32 levels per tree, checked before native recursive serialization. Failed reads and saves remain fatal for that coordinator, preventing a later autosave from treating a bad file as empty; close still releases its lock.

Entity enumeration and serialization run on the owning thread; raw NBT I/O runs on the storage worker. Autosave first loads unknown destination cubes asynchronously, then validates a detached batch and submits up to four cube files per tick. Normal unloading waits across ticks for the batch and rechecks current entity state before releasing objects and UUIDs. Explicit save-all/close drain the batch. Batch capture still enumerates resident entities, so this is not yet a scalable dirty-entity scheduler. Individual files are replaced atomically, but a batch spanning multiple cubes, or block and entity files, is **not** a crash-atomic transaction. An I/O failure or interruption partway through a batch can leave different snapshot generations on disk; there is no cross-file rollback or journal. Duplicate UUIDs on a later load are rejected, not silently resolved. Native entity deserialization/registration callbacks are not transactional either.

Loaded entities are registered as loaded objects through the real native UUID registry and resident sections. The bridge below exposes and ticks them according to full cube status. Tests below demonstrate persistence and lifecycle integration with mocked world services, not a playable save/reload session.

## Live entity visibility, queries, and client tracking

`CubeEntityVisibility` wraps the installed 26.3 manager's movement/removal callbacks and groups entities by full `CubePos` objects. FULL or higher cube status first loads entity data, then starts native tracking. INACCESSIBLE hides entities immediately without prematurely releasing resident objects or UUIDs; successful persistence unload removes them later. Repeated status notifications do not duplicate callbacks. Admission preserves native `onCreated` ordering, removal preserves UUID cleanup, and always-ticking players retain their native lifecycle. Full section comparisons also notify movement between heights separated by 16,777,216 blocks, which pack to the same vanilla section key. ENTITY_TICKING additionally enables native ticking as described below.

Server and client `LevelEntityGetter` spatial operations now scan a snapshot of the native visible-entity lookup and intersect current bounding boxes with the requested AABB. This avoids packed-coordinate truncation, fixed maximum entity-size assumptions, and iteration across enormous coordinate ranges. Typed queries, early abort, native ID/UUID lookups, outer Level predicates/exclusions/limits, movement, and callback-driven removal are preserved. Entities removed or replaced during a query are skipped. Client entity admission and removal still belong to its native transient manager. Ordinary worlds retain their original getter and lifecycle.

This is an O(visible entities) query with an O(visible entities) temporary snapshot, not a scalable spatial index. Native packed sections remain passive resident storage on the server; their Y keys are not used to decide cube visibility or service these Level queries. Direct third-party queries against that internal section storage have not been adapted. A future index must retain exact bounds and oversized-entity behavior while reducing query work.

The native `ChunkMap.TrackedEntity.updatePlayer` entry point routes cubic worlds through the transformed tracker. Its distance test includes Y and retains the native entity/passenger range and broadcast checks. Pairing additionally requires the same server level, the player's full 3D cube view, no pending send, and a successful full-cube send recorded for this sender and level. Sending cube data precedes entity pairing; a failed payload send does not record the cube or expose its entities. Cube send/drop notifications refresh stationary entities immediately. The sender clears recorded cube positions when it sends in another dimension and removes positions on drop. Player cube movement compares full cube keys, so a teleport between aliased section heights still updates distance-manager tickets and tracking view.

These changes reuse vanilla entity spawn/update/removal packets; no block, entity-disk, or cube-packet format changes are introduced. Component tests verify pairing/removal calls and payload order with mocked connections. They do not verify visual rendering, real multiplayer transitions, or a complete world lifecycle.

## Mob ticks, AI, and bounded navigation

Cube status now controls the native `EntityTickList` through `PersistentEntitySectionManager.startTicking/stopTicking`. FULL and BLOCK_TICKING remain visible but do not tick ordinary entities; ENTITY_TICKING starts them. Demotion, movement into a non-ticking cube, and removal stop ticks before stopping tracking. Admission starts tracking before ticking. Always-ticking player behavior remains native. The server's existing per-entity tick body keeps freeze checks, despawning, vehicle/passenger handling, `commonTick`, and `tick`; its distance-manager lookup uses the full cube key and requires current cube ticking status. `isPositionEntityTicking(BlockPos)` also reads full-coordinate status. This is not a second entity simulation loop.

Normal mob ticks reach the existing goal selectors, sensing, navigation, custom AI, and movement/look/jump controls. NoAI and passenger semantics are retained. The void check uses the supported cubic minimum rather than the dimension's ordinary minimum; dimension heights and section-array sizes remain unchanged.

`PathNavigationRegion` uses a bounded `CubeMobBlockView` in cubic worlds, with non-loading `cc_getCubeNow` reads from FULL cubes. It does not read vanilla columns. Block and fluid reads, collision readers, and local min/max Y use that view. Missing cubes, unsupported coordinates, and positions outside the search box act as solid barriers. Native ground, flying, and swimming pathfinders still choose the route. Ground target surface adjustment stops at missing terrain and scans at most 96 blocks. Cubic maximum path length is capped at 96 blocks; vanilla's 8/16-block search padding remains. This favors bounded work over arbitrary long-range navigation.

Path nodes use immutable full `BlockPos` keys instead of the native truncated integer hash. The persistent world `PathTypeCache`, whose packed block keys alias every 4096 Y, is bypassed for cubic contexts. Per-search path classification remains native within the bounded region. The collision iterator now receives a cube-backed block reader from Level or the path region. The inherited `MixinBlockCollisions` retains the cube collision-provider contract and checks implemented interfaces before selecting it; ordinary readers and path regions use the native path without an unsafe cast to `CanBeCubic`. Both readers resolve each block's full Y, and missing terrain behaves as a collision barrier. Entity fluid interaction replaces its column-section preflight with loaded cube sections and uses a non-loading reader for native fluid height/current calculations. Position-aware `hasChunkAt` and six-coordinate `hasChunksAt` queries use cubes, including for negative heights.

These changes enable the main ticking/AI/navigation path for existing mobs. They do not implement cube random/scheduled block ticks, village POI storage and sensors, every species-specific behavior, long-range navigation, teleport/portal searches, or a complete lighting/world simulation. In-game multiplayer/rendering and performance with large mob populations remain unverified. No disk or network format changes are required.

## Natural biome spawning in cubes

The cubic `ServerChunkCache.tickChunks(ProfilerFiller)` route now calls `CubeNaturalSpawner` instead of the inherited empty spawn method and column-based `NaturalSpawner.SpawnState`. The outer native cache tick retains its normal/frozen scheduling; the spawner also checks the tick rate and SPAWN_MOBS rule. Hostile categories respect the native cache spawn setting, persistent categories retain the 400-tick cadence, and MISC is excluded. The existing block-tick dispatch remains; the cube block-tick body is still unfinished. The column-only debug spawn state is cleared rather than misreported.

Candidate discovery checks a bounded 9×9×9 cube neighborhood per non-spectator player, deduplicates full CubePos keys, and keeps centers within 128 blocks in 3D. Candidates require the correct loaded FULL cube instance, ENTITY_TICKING status, the entity manager's ticking permission, and the world border. Reads never request cube loading. Each category samples all three coordinates uniformly inside the cube; no dimension minimum or column heightmap selects Y. Pack walks recheck readiness and distances for every candidate, including when crossing a cube boundary. Player exclusion is 24 blocks, the outer radius is 128, and the world respawn exclusion uses full Y and the current dimension.

The explicit cubic cap policy grants one vanilla category allowance per eligible player globally and at most that allowance around each player within 128 blocks. Overlapping players count nearby mobs for each local allowance; every vertical layer shares those allowances. This is not vanilla's 289-column density formula, and population balance/performance still need gameplay testing. Existing visible nonpersistent entities are counted first, and successful admissions update caps immediately, including passenger trees. Cube biome reads now choose the XYZ section and its local quart coordinates; LevelReader no longer queries a column for cubic noise biomes. Native SpawnPlacements, species rules, mob obstruction checks, collision, group finalization, and entity-manager admission remain in use. Packs retain three group attempts and native group/cluster limits, with an additional maximum of 64 attempts per group to bound data-driven counts.

Each attempt requires a current fully exact cube light publication. A scoped reader makes native block/fluid/light queries non-loading, rejects missing data, and uses bounded cube-backed liquid checks. Predicates asking for a global heightmap defer the attempt because a local cube cannot prove the global surface. The scope is removed even on exceptions. Ordinary worlds do not use this scope or the cubic scheduler.

This implements regular spawning within ready areas. Structure overrides and the four built-in special spawners are covered below; generation-time spawning and general rules needing a global surface remain separate work. The later automatic lighting manager supplies ready areas around tracked players; exhaustive spawning gameplay remains unverified. This spawning milestone introduced no disk or network format changes.

## Special spawners and structure lists

`CubeStructureSpawns` resolves a cube's own starts and its reference sets with full CubePos keys. Only loaded FULL owner cubes are read; missing referenced owners/starts or more than 1,024 relevant references defer the query. Valid starts are deduplicated. Structure-category overrides retain PIECE versus whole-STRUCTURE bounding-box tests, including explicitly empty lists. The nether-fortress nether-brick rule checks the full structure box before normal overrides, as in 26.3. Pack selection and subsequent membership checks use the resulting list, while density costs remain biome environment attributes. This is a spawning query adapter, not a replacement for the global StructureManager, generation, or locate commands.

The cubic cache tick now dispatches the existing ServerLevel custom-spawner list after block-tick dispatch, under normal ticking and SPAWN_MOBS. The four built-in spawners route cubic levels through the adapters; ordinary worlds retain their native code. Third-party CustomSpawner implementations still receive the normal dispatch and have not been adapted or tested.

Phantoms retain their cooldown, hostile/phantom rule, darkness, difficulty, insomnia threshold, and group size. In a sky-lit dimension, exact local sky exposure replaces the absolute sea-level cutoff, allowing exposed terrain at negative cubic heights. ## Cube POI storage and villager behaviors

The existing `PoiManager` remains the API used by villagers and special spawners. Cubic managers route position operations and range queries through `CubePoiStorage`; native `PoiSection` and `PoiRecord` still own types and ticket counts. Storage groups the eight sections by full CubePos. No section/block Y is decoded from vanilla packed keys. Range and closest/random/type-filtered queries are 3D; the former horizontal square query becomes an XYZ box. Oversized queries fail before I/O at a budget of 16,384 cubes, negative radii are rejected, and endpoint clipping/radius arithmetic avoids overflow. Column-only debug enumeration reports resident sections without attempting an infinite vertical scan.

Native acquisition/release and occupancy predicates are preserved. Registered HOME, workstation, MEETING, and other POI types use the same code. Village sources are sections containing occupied records tagged VILLAGE. The native 26-neighbor distance is computed as the minimum Chebyshev section distance to resident sources, capped at seven; ticket changes, reads, removals, and unloads update those sources immediately. Queries load saved POI only. `ensureLoadedAndValid` is the explicit terrain-loading path, requests cubes rather than columns, and retries unavailable cubes. Newly loaded/generated FULL cubes, disk-read cubes, and save snapshots reconcile POI against section palettes. Matching position/type records retain claims; removed or changed types lose old claims. Direct cube block edits and the ServerLevel block callback update POI idempotently, preventing duplicate callbacks from resetting tickets.

The separate `cube_poi` directory uses ordered atomic compressed cube files through `CubeStorage`. Format `cubicchunks:poi`, version 1, stores the game DataVersion, cube size/position, all section records, validity, native registry types, full BlockPos coordinates, and free tickets. Reads validate every section before publishing any of the cube: unknown versions/types, wrong positions, duplicates, out-of-section records, and invalid ticket counts fail. This format has no migration/data-fixer support; vanilla POI regions remain separate. Tick-budget flush, save-all, per-cube saves (including ticket-only changes), unload, and close are connected to the native cache lifecycle. Failed writes retain dirty state and surface on later operations/close; stores release their locks even after failure. Atomic replacement applies per POI file, not as a transaction across terrain, POI, and entity files; block reconciliation repairs stale POI against authoritative terrain.

AcquirePoi, SetClosestHomeAsWalkTarget, and NearestBedSensor retain their native control flow, path searches, retry timing, and memory updates. Their per-behavior retry maps now use opaque keys assigned to full immutable BlockPos values. These keys are never interpreted as positions, persist only in each retry cache, and discard expired auxiliary mappings periodically. This identity fix also applies to ordinary-world retry caches without changing their behavior rules; ordinary-world PoiManager storage, range semantics, and lifecycle remain native.

POI tick saving uses a bounded queue of detached snapshots and applies acknowledgements on the owner thread. Claims changed while a snapshot is pending remain dirty for the next write. Flush/close wait explicitly; normal cube unload retries until POI is saved. Queried POI cubes remain in memory until cube unload or manager close. Large-area indexing, cache eviction for POI-only reads, and I/O performance need further work. The initial POI tests exercise native villager acquisition, profession assignment, release, bed sensing, and invalidation. Sleep, restocking, meetings, their relevant networking, and iron-golem summons are covered by the following milestones; complete village schedules, raids, developer debug packets, and an end-to-end playable village remain unverified. Block ticking, full generation and complete village gameplay remain separate work.

## Functional blockers

1. **Global heights, lighting and rendering:** automatic per-cube sky/block light now works with the current deterministic hills generator, including saved unloaded roofs and dependent-column updates. Packed render-section Y still aliases at extreme heights. Global world-height APIs, arbitrary generator support, incremental propagation, persisted light arrays and large-world performance remain unfinished. Invalidated or pending server light remains unavailable/zero; client display retains a previously accepted field during relighting.
2. **Simulation and live entities:** cube persistence, full-coordinate visibility/spatial queries, 3D client tracking, native mob ticks/AI, and bounded navigation now exist. Cube block ticking, generation-time spawning and global surface predicates, complete village gameplay, specialized behaviors such as teleport searches, complete environmental interactions, and persisted forced-cube state still need implementation and integration tests. The current linear entity query also needs a scalable index for large populations.
3. **Generation:** seeded hills and full-coordinate biomes now support initial entry. Caves, aquifers, ores, vegetation, structures and generation-time spawning remain unfinished. Other terrain presets are not implemented by the cubic terrain generator.
4. **Storage performance and migration:** autosave now has bounded asynchronous acknowledgement, but still uses one file per cube and owner-thread snapshot capture. Large-world throughput, packed-region storage, and importing older worlds are not implemented or validated.
5. **Remaining networking and debugging:** block deltas, full-cube block-entity snapshots, destruction/use-on-block actions, direct corrections, prediction reconciliation, sign/command/structure editing, bounded structure corner detection, and template capture/placement with resident entities preserve extended heights. Other specialized packets, cube debug subscriptions, command execution, and full live-entity gameplay still need wider cubic integration.
6. **End-to-end validation:** initial singleplayer creation, entry, a saved block and reopening are tested. Long traversal across cube boundaries and extreme heights, complete entity/village simulation, multiplayer, dimension transitions and visual correctness still need gameplay tests. Compatibility with Sodium and other mods is untested.
