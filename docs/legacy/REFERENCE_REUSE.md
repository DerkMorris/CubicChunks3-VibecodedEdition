## Pinned Core surface tracker tree

Core revision `75a1100c8a6d47f02bde8515d4a7de207f04be36` contains a surface tracker tree and interleaved disk storage. They are **not wired into this milestone's heightmaps**. The new `CubeHeightmap` uses Minecraft 26.3 predicates and `SimpleBitStorage` for six local 32×32 maps. It does not reuse the tree algorithm or claim global column heights.

The tree's 16×16 leaves and `HeightmapSource` contract are possible starting points for more efficient column aggregation. A 32-block cube would contribute four horizontal leaves, with additional persisted column roots, load/unload handling, and client synchronization. A local map alone cannot determine whether a higher, unloaded cube contains the world's surface.

The new `ColumnSurfaceIndex` instead combines detached local maps over an explicit cube-Y range. It reads unloaded observations from existing cube files and overlays live FULL cubes captured on the server thread. Missing and provisional cubes remain unknown. This avoids adopting Core's separate persistence backend before its correctness issues are repaired, and avoids introducing a second file that could disagree with saved blocks after a crash. It is not a cached tree or a completed skylight implementation. No Core tree or storage code was changed for this milestone.

Source review of [InterleavedHeightmapStorage](CubicChunksCore/src/main/java/io/github/opencubicchunks/cc_core/world/heightmap/surfacetrackertree/InterleavedHeightmapStorage.java) identified issues that must be addressed before adopting that storage:

- `close()` sets `isClosed` before calling `flush()`, whose closed check returns without flushing.
- `writeNode()` sets one bits but never clears previous bits when new encoded heights contain zeros.
- `saveNode()` reads an existing compressed file directly as a bitset, whereas `loadNode()` inflates it first.
- `flush()` removes a cache entry before its compressed output stream has closed successfully, so a close failure can discard the retry copy.

These are source-review findings, not newly executed regression-test results. Existing cache-based Core tests do not establish fresh-instance close/reopen correctness. Focused tests for rewrites, close, reopen, and failure retention are required before wiring this backend into world heights. No Core heightmap tree or storage code was modified for the local-heightmap milestone.

## Minecraft 26.3 skylight adaptation

The bounded milestones below are historical. Normal gameplay now uses `CubeWorldLightManager`, `CubeWorldSkyColumn` and `CubeWorldLightSolver`: automatic tracked-cube scheduling, a complete direct-sky index for the current hills generator, and exact propagation through a 15-block halo. Saved and live section data override the deterministic generator; unloaded roofs remain authoritative. The native 26.3 edge/attenuation rules are reused and compared against its real engine in tests. No old Phosphor engine or Core tree persistence was copied. A new per-cube revocation protocol preserves unrelated publications; the full-cube outer wire format is 4. Light arrays still are not persisted. New generator features will require replacing the deterministic fallback, and extreme-height renderer coordinate packing remains unfinished.

The 2026-10-29 display follow-up separates the client's last accepted visible light from current readiness. Relighting keeps that immutable field visible until a validated replacement arrives; cube eviction removes it. This fixes black update flashes without changing server light validity, propagation rules or packet/storage formats, and does not copy an older lighting engine.

The subsequent scheduling optimization shares versioned sky indexes, admits bounded batches of detached cube jobs, prioritizes local edits, and supplies exact light with initial cube transmission. Row copying, uniform-section capture and frontier seeding optimize this port's existing solver; no CC1/CC2 engine or persistence format was imported. Native 26.3 parity and stale-publication tests remain the correctness checks.

The client prediction follow-up uses new bounded removal and increase queues over loaded cubes and immutable visible light. Native 26.3 emission, dampening and opposing-face occlusion determine provisional light after opening or obstructing cells and changing emitters. Old block faces identify former light dependencies; remaining emitters and neighboring sky refill the removed region before one atomic publication. Fresh native-engine comparisons cover both layers through roof changes, torch removal, water and slabs. Full relight snapshots replay unacknowledged local block/entity states and retain the incoming authoritative baseline for acknowledgement. Neither mechanism copies CC1/CC2 code or changes packet/storage formats.

The new `CubeSkyOcclusion` and `ColumnSkyLightIndex` follow the actual 26.3 `ChunkSkyLightSources` edge rule: lower-block light dampening, then occlusion of the upper downward and lower upward faces. They do not substitute a normal heightmap predicate or copy the old Phosphor engine. Unlike the older approach that may substitute air for an unavailable neighbor, a cross-cube edge is checked only when both FULL snapshots are available. Missing coverage stays explicit.

Existing saved sections supply the internal edges and both boundary-state planes, so the occlusion milestone needs no new persisted summary format. Neighbor-dependent edge results are computed when combining snapshots. This obstacle-query API does not establish an open upper sky boundary or compute propagated light. The old maximum-brightness cubic fallback has been removed.

## Bounded propagation and lifecycle adaptation

The new `BoundedCubeLightSolver` is a finite 3D calculation using actual Minecraft 26.3 block emission, destination light dampening, and opposing face-occlusion shapes. Ordinary transfers attenuate by at least one; unoccluded downward level-15 sky light retains level 15 when the destination has zero dampening. It uses full detached block-state snapshots rather than treating a local heightmap or the highest direct-sky edge as sufficient information for lateral propagation. No legacy Phosphor implementation was copied.

Unknown exterior inputs and missing interior cubes produce lower and upper light bounds. Equal bounds establish an exact sample; missing cubes remain unsampled. The detached solver supports explicit exterior observations, while the production server manager uses only `CubeLightBoundary.UNKNOWN`. The legacy unloaded-neighbor and surface-change algorithms remain references for future work; the current server path does not assume that an unavailable neighbor is air or that a bounded clear column reaches the sky.

The asynchronous server API captures only FULL cubes in the active updating-holder map, with a limit of 27 cube positions and 1,048,576 cells per domain. It retains one active rebuild, rejects parallel requests, and replaces its single publication when a rebuild is accepted. Busy or pre-capture-invalid requests do not retarget the selected area; an admitted request's future still describes just one attempt. The manager records holder/cube identity, status, block revision, and missing coverage for every position, retaining that watch after publication is revoked or an empty area is calculated. Edits, unloads, replacements, and newly available dependencies make the result stale. This uses current holder APIs rather than the old asynchronous lighting or dirty-state handling.

The current engine bridge consumes immutable `CubeLightView` data: exact scalar cells can be read from an otherwise uncertain cube, a `DataLayer` requires a complete exact section/layer, and raw brightness combines both ranges before testing exactness. Disabled layers remain disabled. Server live validation stays on the owning thread; off-thread server reads return unavailable/zero instead of touching mutable holders. Block edits revoke stale publications immediately. Normal server ticks coalesce changes into at most one fresh solve of the last admitted area, including a later retry after a stale completion. Stable empty or uncertain areas do not loop, and no new world areas are selected automatically.

Calculation failures retry after 20, 40, 80, and 160 ticks, then pause at five consecutive failures until dependencies change or an explicit rebuild is admitted. Status reports calculation phase, counters, and delay separately from notification failures. Failed notifications retain the latest epoch and an old/new domain union of at most 54 positions, retrying after 20 ticks without a new solve; a pending notification blocks retargeting to a different domain. These bounded scheduling and recovery rules are new code, not a reuse of legacy Phosphor scheduling.

The full-cube wire format is now version 4 and carries an optional exact pair of cube-sized block/sky fields with the full block and block-entity snapshot. Sixteen fixed 2,048-byte section arrays contribute 32 KiB of light data. Custom revocation epochs precede replacement snapshots; vanilla column light masks and the old transformed light-packet constructor are not used. Client callbacks validate world, cube identity, local block revision, epoch, and cache generation. Accepted complete light drives transient render readiness and section dirtiness without setting `isLightCorrect`.

Client block changes conservatively revoke all cached light views and require a newer server epoch, even when the edited cube is outside the server's bounded publication. Cache eviction instead advances only the local callback generation and clears light; a fresh full snapshot may restore the same server epoch. This distinction prevents queued work from resurrecting an evicted entry without permanently rejecting valid server data.

Limited client recovery retains one cached anchor and sends at most five requests at cumulative eligible client ticks 20, 60, 140, 300, and 500. A complete full packet registers that anchor after its blocks are installed, so even the first queued light callback can recover if a subsequent edit rejects it; this exposes no light and does not reset an existing timer. Packets without light do not register this expectation. Requests require the current connected cubic world and payload support, stop if the anchor disappears, and cancel when its ready light arrives. The version-1 serverbound payload carries only position and observed epoch. The server verifies current player/world membership, tracking, coordinates, and epoch, and permits one successful recovery per 20 normal world lighting ticks. Recovery republishes already exact current views at a new epoch; it neither selects bounds nor loads cubes or starts a solver. It may give up without recovering when the server remains unready. Recovery uses the current full-cube wire format.

The disk format remains unlit and unchanged, `isLightCorrect` remains false, the production sky boundary remains unknown. Automatic area selection, incremental propagation, verified sky inputs, cross-domain updates, persistent lighting, and a complete gameplay lifecycle still require integration. No old Phosphor or RegionLib lighting implementation was transplanted.

The later broadcasting fix follows the installed Minecraft 26.3 block-change and send-readiness methods rather than copying an older mod's packets. Cube holders use eight XYZ section slots. The obsolete transformed column-light packet branch is removed. Send readiness keeps 3D player tracking and cache notification while registering column-based debug subscriptions only for ordinary chunks. This closes the two previous missing-member audit findings without adding cube debug overlays.

The subsequent block-delta protocol is new code: a canonical cube key, XYZ section index, and local block positions avoid vanilla's packed world-coordinate truncation. It pairs registered block states with bounded normal block-entity update tags and splits large batches. The client mutates only loaded cubes directly, uses 26.3 component-aware NBT loading, and preserves revision-based light invalidation. It does not transplant the older mods' packet layouts or claim compatibility with them.

The player-action extension also uses new code against Minecraft 26.3: full-coordinate envelopes reconstruct vanilla destruction and use-on-block packets in memory, retaining the current server validation logic and sequence acknowledgements. Client prediction keeps vanilla sequence/teleport semantics with per-world full-coordinate keys, cube-identity checks, and deferred block-entity data. Earlier Cubic Chunks packet layouts are not reused.

Full-cube block-entity snapshots now follow the 26.3 initial synchronization contract: every entity block contributes its type and `getUpdateTag`, including empty tags and instances promoted from pending saved NBT. Saved inventory data and the optional per-change packet are not used for initial transfer. A section/local position preserves full cube coordinates; the new bounded format does not reuse legacy packet layouts. The client prepares sections and fresh entities before replacement, registers them through the current cube lifecycle, and clears stale objects, tickers, and pending tags on replacement or unload. The full wire versions advance to outer 3 / inner 2; disk format 2 is unchanged.
